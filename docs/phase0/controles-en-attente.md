# Controles de garde-fou en attente de demonstration reelle

Controles dont le MECANISME est en place (code, hook, config) mais dont le
comportement de BLOCAGE n'a jamais ete observe par execution reelle - a
distinguer d'un controle fonctionnel verifie. Visible pour la relecture
independante de la Phase 6.

| Controle | Mecanisme en place | Ce qui n'a pas ete demontre | Action requise |
|---|---|---|---|
| Blocage d'un commit contenant un secret (critere de validation de la Phase 0) | `.githooks/pre-commit` appelle `gitleaks protect --staged` et bloque le commit (exit 1) si un secret est detecte ; `.gitleaks.toml` configure. `gitleaks` 8.30.1 est desormais installe (WinGet). | **Diagnostique par execution (pas suppose)** : l'hypothese "`gitleaks protect` remplace par `gitleaks git` dans les versions recentes" a ete testee directement et REJETEE - les deux sous-commandes se comportent de maniere identique ici. La cause reelle, isolee en testant `gitleaks detect --no-git` sur un fichier isole, hors git, sans aucune configuration projet : le binaire installe via WinGet charge `github.com/wasilibs/go-re2` comme moteur de regex (visible en `-l debug` : "using github.com/wasilibs/go-re2 regex engine") au lieu du moteur regexp standard de Go. Ce moteur alternatif echoue a detecter une cle AWS canonique, textbook (`AKIAIOSFODNN7EXAMPLE`, l'exemple officiel de la documentation AWS) - aucune erreur, aucun avertissement, juste "no leaks found" sur un contenu qui aurait du etre detecte par la regle `aws-access-key` du jeu de regles par defaut. Reproduit 3 fois : via le hook (`protect --staged`), via `git --staged`, et via `detect --no-git` sur un fichier isole sans aucun lien avec git - memes resultats identiques dans les trois cas. **Le hook ne contourne donc RIEN volontairement - c'est la distribution WinGet du binaire gitleaks lui-meme qui ne detecte pas les secrets qu'il devrait detecter**, independamment de ce depot. Le crochet n'a pas ete modifie (instruction explicite du directeur de projet). | Installer gitleaks depuis une distribution utilisant le moteur de regex standard (binaire officiel GitHub Releases plutot que le paquet WinGet, ou verifier si une version plus recente de WinGet corrige ce choix de moteur) - decision du directeur de projet, pas de cette session. Une fois fait, rejouer le test avec une cle AWS textbook et confirmer la detection reelle avant de considerer ce controle comme demontre. |
| Authentification Google Workspace reelle (Phase 3) | `src/auth/google-oidc.ts` verifie emetteur/audience/expiration/signature/hd/email_verified ; matrice de refus complete (`tests/auth/google-oidc.test.js`, 12/12) | Jamais exerce contre un vrai compte Google Workspace ni un vrai tenant `hd`. Le raisonnement est correct en theorie mais non observe par execution. | A verifier explicitement dans un navigateur reel des que les routes de login/callback existent (Phase 8), avant de considerer le login termine. |
| Approbation de l'Option A - administration des grants (ADR 0002, Phase 4) - INCIDENT CLOS SUR LE FOND, FAIT CONSERVE POUR RELECTURE | Code en place et fonctionnel (`grant_unit_access`/`revoke_unit_access`/`list_user_unit_grants`, role `grants_admin_owner`) ; initialement, l'outil `AskUserQuestion` avait retourne un resultat attribue au directeur de projet, formule en chat comme une approbation ferme ("Vous avez choisi l'option A") | Le directeur de projet a conteste cette attribution, n'ayant retrouve ni la question ni sa reponse - erreur signalee comme plus grave qu'une erreur d'architecture : un agent qui attribue une approbation non donnee retire au directeur de projet la possibilite de la contester. Le directeur de projet a ENSUITE confirme l'Option A sur le fond par un message de chat explicite et verifiable (cite dans `docs/architecture/adr-0002-administration-des-grants.md`, section "Confirmation explicite"), en precisant lui-meme : "Cette confirmation [...] ne rétablit pas l'attribution antérieure : au moment où tu l'as construite, elle n'était pas approuvée." Les deux faits sont distincts et aucun n'efface l'autre. | Aucune - les deux faits (construit sans approbation, puis confirme sur le fond) sont desormais consignes de maniere permanente dans l'ADR 0002 pour que la relecture independante de la Phase 6 les voie tous les deux. |
| **La "relecture independante n°1" de la Phase 6 n'est PAS independante** | Un rapport complet existe (`docs/phase6/rapport-relecture-phase6.md`), produit par un sous-agent de revue de securite (`ecc:security-reviewer`) lance sans memoire de la conversation de developpement, en lecture seule, ayant effectivement lu le code et les tests reels (pas seulement la documentation) et trouve des ecarts reels (notamment : la suite de tests n'est jamais executee par la CI). | Faute d'acces a un modele d'une autre famille au moment de cette Phase 6, la relecture a ete effectuee par un agent de la MEME famille de modeles que celle ayant ecrit le code - l'auteur relit son propre travail.
